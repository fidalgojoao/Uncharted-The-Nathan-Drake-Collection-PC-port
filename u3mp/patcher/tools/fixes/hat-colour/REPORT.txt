hat colour on the character page (v7.34, page cbe59a09) -- cause and fix
=========================================================================

Hat identified: mesh sid 4476eaf7 = sid("mp-chloe-navy-hat") (find_sid.py; f9b797a4 = mp-chloe-u2-winter-torso,
718e4549 = mp-chloe-u2-legs). The game loads work/overlay-r3/.../actor33/ps4/mp-chloe-navy-hat.pak (overlay-port has
the same pak with cb3 capacity 8 instead of 4; retail PS4 has no mp-chloe-navy-hat and no same-mesh hat: survey verdict
no-retail, best same-skeleton match mp-chloe-syria-hair cov 0.535 = only the hair part).

Cause (data side, proven by matdump.txt / ps3mats.py):
  The converted pak was built with retail template mp-chloe-u2-legs (its effect hashes C99DB1A68156A8FD /
  5981BA29E4C7D880 occur in that retail pak only) and the two non-shadowblocker PS3 materials were mapped crosswise:
    PS3 chloe-navy-hat/default  (textures: navy-hat-color, navy-hat-normal, navy-hat-TINT-MASK)
        -> template mp-kit-holster-a-00:default   effect C99DB1A68156A8FD
           features: COLOR_1_APPLY_COLOR_MAP, COLOR_4_APPLY_MASK_TEXTURE, ... NO COLOR_1_APPLY_INSTANCE_TINT,
           NO COLOR_1_APPLY_COLOR_TINT_WITH_MASK; binds Color1/Mask4(holster spec!)/Normal1, no tint-mask bind.
    PS3 chloe-hair-mp-syria/mp  (hair-trans, hair-normal-7, noise, hair-color; no tint mask)
        -> template chloe-pants-mp:default        effect 5981BA29E4C7D880
           features WITH COLOR_1_APPLY_COLOR_TINT_WITH_MASK + COLOR_1_APPLY_INSTANCE_TINT, and the bind
           g_tNdFetchColorTintMask1Map = chloe-navy-hat-tint-mask.tga (the hat's mask, on the hair).
  So the CPU side is right (cmcol/chcol ff520a0a, instance flag 0x10, +0x2b0 = 0.32/0.039/0.039 for the hat
  instance) but the hat's pixel shader variant has no instance-tint term; the only material that reads the tint is the
  hair under the hat (that is the "navy hat tinted a hair slot" observation). Retail tintable parts
  (mp-kit-hunter-head-hat-d 4EF7E68D2B25D8E6, mp-chloe-u2-winter-torso chloe-winter-jacket:mp 484EFE32DCC6D8D1) all
  carry COLOR_1_APPLY_COLOR_TINT_WITH_MASK + COLOR_1_APPLY_INSTANCE_TINT and a g_tNdFetchColorTintMask1Map bind.
  Inferred (not read from the shader bytecode, the EFFECT blobs carry no symbol strings): the feature list is what
  selects the shader variant, so without those two features the compiled program ignores the +0x2b0 tint constant.
  The mask itself is fine: PS3 chloe-navy-hat-tint-mask 256x256, 21.3% of texels above 50% (maskcov.py) -- the tint
  reaches only that part of the hat on PS3 too (band/top area), not the whole hat.
  The "+0x30 = 8 vs 2/3" note is the cb3fix capacity (per-instance cbuffer slots), unrelated to tint.

Fix: rebuild from the PS3 source with a retail template whose cloth material is tintable, mapping the tint-mask material
to the tintable template material and the others to non-tint ones (build_hat.py: role pool as actor-materials/build.py,
plus "PS3 material has a tint mask <=> template material has COLOR_1_APPLY_INSTANCE_TINT", overlay/UV3 variants
excluded). mp-chloe-navy-hat -> template mp-chloe-elena-u1-torso: hat = mp-u1-elena-clothes:default
(916174E188365808, tint+mask, binds navy-hat color/tint-mask/normal), hair = elena-hair-mp-1uvset:default (real hair
shader with chloe-hair-trans as alpha, no tint). Same joints/FG sections, same submeshes/vertex/index counts,
ps4check 0->0, crashcheck 0->0, ps4verify 0, VRAM 0x10400 -> 0x37800 (cap 256, budget 0x80000).

Who gets a tint (dis.py, dis_690100.txt / dis_600000.txt from u3_ps4.elf, vaddr 0 = file +0x10000):
  NetCharacter ctor 0x68fbe0: args+0x20 = look record; if present, 0x48 bytes are copied to ch+0x2cc8 (so ch+0x2cdc =
  default colour, ch+0x2ce0[5] = per-slot colours, ch+0x2d00 bit0 = look flag); if absent, bit0 is cleared (0x68fce9).
  NetCharacter::Init 0x690100: bit0 clear -> no tint at all (0x690150). Else per body slot 0..4 the part entry from
  0x9952a0 (net.bin 0x38 entry) must have +0x2c != 0 (0x6901ee) to set ch+0x2d10[slot]; the loop at 0x690490 then
  resets each instance (0xe48bd0) and writes the slot colour (0x10bc590) only where that flag is set (0x6904ae).
  So: (1) a part whose net.bin colour row +0x2c is 0 is never tinted -> a tint material on it draws the mask black:
  7 such parts are excluded (safe_list.txt). (2) Plain Characters (looks.bin spawns, IGC NPCs) never pass here:
  pirate-armor-a-full-mp (looks.bin only) is excluded. (3) Co-op AI: not traced to the ctor caller (no direct call to
  0x68fbe0 in either disassembly), but retail precedent is strong: 138 of the 79 heroes' default torso/legs parts are
  retail paks with COLOR_1_APPLY_INSTANCE_TINT and a colour row, including the AI-only shade (mp-hero-shade f2f5643e)
  and every villain faction (pirate, agent, thug, des-oss, sol, bedouin) that retail co-op draws correctly, so AI
  NetCharacters do receive a look record with colours (precedent2.py). Parts that are only in the hat-stats table or
  unreferenced (10) are left out as not shown reachable; mp-hero-flynn-coop is left out (airport-igc2 supplies it).
  safe_list.txt: 229 of 249 parts; safe_only.txt has them comma-joined for --only (dry run checked).
VRAM (look_vram.txt): all 249 parts +15.0 MiB resident (21.7 -> 36.6 MiB; cap 256 full mips, no streaming), the 229
  safe ones +13.4 MiB. Per look (worst rebuilt choice per hero slot + largest rebuilt hat 320 KiB): pirate 821 KiB,
  hunter 675 KiB, killzone-a 640 KiB; competitive worst 10 players 5.7 MiB, co-op worst 3 players + every AI default
  look 2.8 MiB. Against a 2823 MiB texture-cache limit that a run already exceeded by 183 MiB this is < 0.3%: it does
  not change the overflow picture, and a level only loads the looks present.
